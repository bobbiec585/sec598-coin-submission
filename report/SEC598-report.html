SEC598 · Coin challenge · Proof of concept

From threat intelligence to security validation

I built an evidence-led pipeline using AI, Terraform, Ansible and a disposable AWS lab.

7 November 2026 · Microsoft Threat Intelligence: Exploitation of CVE-2026-73570 in Zimbra Collaboration Suite
01 · Executive summary

What I set out to prove

I wanted to explore how AI and security automation can turn published threat intelligence into repeatable, evidence-backed security validation. The longer-term aim is a pipeline that ingests selected reporting, identifies useful adversary behaviours, builds a temporary test environment, executes controlled tests, assesses what defenders can see and tears everything down.

For SEC598, I focused on proving the structure rather than building a complete red- and blue-team platform. I used source-specific parsing, structured AI extraction and human approval to drive a Terraform-provisioned, Ansible-configured AWS lab. I started with two basic tests to demonstrate the validation and reporting stages.

Both tests reported successful execution and relevant Linux telemetry. Detection effectiveness was not tested. The pipeline reported successful teardown.

02 · Overview and goals

A platform, not two isolated tests

My intended end state is automated CTI ingestion and analysis, targeted adversary emulation, richer defensive telemetry and evidence-based detection validation. I kept the initial red- and blue-side implementations deliberately small to prove the structure before adding complexity.

My focus for this iteration: demonstrate the CTI → analysis → approval → provision → execute → assess → destroy flow, with analyst control and reproducible infrastructure. I left automated source monitoring and more advanced testing agents for future work.

03 · Implementation

What I built

01Source parsing

I wrote an HTML parser tailored to the Microsoft article structure, stripping unrelated page material before analysis. I currently save and supply the article manually.

02CTI analysis and selection

I used OpenAI to extract behaviours, ATT&CK candidates, source evidence and uncertainties into a structured schema. I matched these to supported tests and checked source quotations before approval.

03Terraform

I used Terraform to provision isolated EC2, network, IAM and transfer-bucket resources. A run-specific state key keeps the disposable environment separate from my original lab.

04Ansible

I used Ansible over AWS Systems Manager to configure auditd and its rules without opening inbound SSH. This captured process execution and systemd unit activity.

05Basic red/blue tests

I ran two predefined, harmless tests as stand-ins for future emulation. I collected SSM execution results, parsed audit events and used AI to assess the evidence.

06Reporting and teardown

I automated test artefact cleanup and Terraform teardown, retaining the assessment, evidence, run logs and recovery details. Teardown is attempted even if an earlier stage fails.

Further implementation detail is in the project repository (public submission copy).

04 · Demonstrated results

What the tests showed

The source report covers several Zimbra compromises. I have not assumed that every reported behaviour occurred on one host, and I tested safe analogues rather than the exploit itself.

T1105 · Ingress Tool Transfer

Command-line retrieval

Assessed and cleaned up

Reported: Attackers retrieved payloads using utilities such as wget and curl and executed downloaded content, including by piping it to a shell.

Safe test: A harmless curl download to a unique temporary file.

BehaviourConfirmed
ExecutionConfirmed
TelemetryConfirmed
DetectionNot tested

Selected audit evidence (1 event)

  • auditd recorded /usr/bin/curl with the expected URL and output path.

Assessment: The supplied evidence supports successful retrieval to a non-empty local file using curl. Execution and telemetry are confirmed; detection is not.

Not demonstrated: No Zimbra exploit, malicious payload, C2 or pipe-to-shell execution.

Source excerpts, detailed findings and uncertainties

Source-verified excerpts

  • “Remote content retrieved with wget or curl and piped to a shell for execution.”

AI findings

  • Process telemetry records /usr/bin/curl running with --output targeting /tmp/sec598-curl-20261107T154749Z-472847.txt and https://example.com as the URL. This directly supports that the expected curl command was executed and appeared in the supplied telemetry.
  • The SSM execution result reports Success and response_code 0. Its command runs curl, then tests that the output file is non-empty, and finally prints SEC598_CURL_TEST_OK; that marker appears in stdout. The successful sequence supports that curl completed and the local output file was non-empty.

Uncertainties

  • The telemetry does not establish the exact contents of the downloaded file or independently verify that they came from the intended remote source.
  • No evidence shows that a detection rule or analytic fired.
T1543.002 · Systemd Service

Systemd service creation

Assessed and cleaned up

Reported: Attackers installed and enabled a systemd service named zimlog.service for persistence, assigned it to the Zimbra service account, and changed its timestamps to resemble existing services.

Safe test: A harmless one-shot systemd unit that creates a marker file.

BehaviourConfirmed
ExecutionConfirmed
TelemetryConfirmed
DetectionNot tested

Selected audit evidence (2 events)

  • auditd recorded successful systemd unit-file creation.
  • auditd recorded the service's harmless touch command (parent PID 1, consistent with systemd).

Assessment: The supplied evidence supports that the unit file was created and its configured touch command executed successfully. The expected behavior is observed in the telemetry. Detection is not confirmed because no analytic or detection alert is provided.

Not demonstrated: No original payload, timestamp camouflage or proof of persistence across reboot.

Source excerpts, detailed findings and uncertainties

Source-verified excerpts

  • “The service was enabled with systemctl enable, establishing execution at system boot, and its status was subsequently checked.”
  • “Its timestamps were then modified to match existing systemd services, including rsync.service and sshd.service.”

AI findings

  • A successful file_create event records root creating the unit file at /etc/systemd/system/sec598-coin-20261107t154804z-075e40.service. Directly supports that the systemd unit file was created.
  • The supplied unit definition configures ExecStart as /usr/bin/touch /tmp/sec598-systemd-20261107T154804Z-075e40.ok. The systemd context reports Result=success, ExecMainStatus=0, and that exact ExecStart with PID 2493. An execution event records the matching touch command with PID 2493. The matching command, PID, and successful systemd unit result support that the configured harmless command executed.
  • The systemd context reports ActiveState=active and UnitFileState=enabled. The SSM result also reports success, and the marker file is present. Explicitly supports that the unit was enabled and active at the time of the supplied context, and that the command's expected marker was created.

Uncertainties

  • The telemetry supports the unit being active when its state was collected; it does not establish that the unit remains active afterward.
  • No evidence shows that a detection rule or analytic fired.
Important: telemetry visibility is not the same as detection coverage. I did not test an EDR analytic, alert, Sigma rule or MDR response in this proof of concept.

Teardown verification: I checked the run-specific Terraform state on 10 November 2026 and found no managed resources. This is my recorded check, not a fresh query by the report renderer.

05 · Future development

Building on the framework

I plan to build on the deliberately small implementations using tools and techniques from SEC598, while keeping the working lifecycle.

CTI and orchestration

I want to pull reports from selected sources, improve parsing and prioritise useful TTPs. I also plan to explore CrewAI, used on the course, to coordinate specialist agents.

Red-side emulation

I plan to expand beyond the two basic tests using Atomic Red Team, MITRE CALDERA and suitable AI-assisted penetration-testing tools.

Blue-side validation

I want to collect richer telemetry and use AI agents to propose detection logic and Sigma rules, then test those detections against actual events.

Lifecycle and outcome

I'll keep the disposable lab and consolidated reporting, extending my assessment from “Was the behaviour visible?” to “Did the proposed detection work?”
